## 一、概述

本工具输入一个社区中心点，输出一份可复现的社区步行可达性体检报告，包含三部分内容：

1. **步行等时圈**：基于真实路网计算 5 / 10 / 15 分钟可达范围（不是直线缓冲圈）；
2. **设施覆盖统计**：8 类民生设施的数量、密度、最近一处的步行耗时；
3. **服务盲区**：步行路网距离超过 1 km 的成片区域，以及补点建议。

单次分析耗时约 8 秒（离线快照模式），消耗地点检索配额 2 次。

---

## 二、问题背景

《城市一刻钟便民生活圈建设指南》等文件要求居民步行 15 分钟内可获得基础医疗、教育、购物等服务。目前社区层面的可达性评估存在两个问题。

**一是用直线距离代替真实可达性。** 道路不是直线。红绿灯、过街天桥、河道、封闭小区都会改变实际步行范围。在本次实测的广州软件学院点位中，直线距离 275 m 的地标，实际步行距离为 1339 m（4.46 倍）；而直线距离 507 m 的地标，实际步行距离仅 603 m（1.21 倍）。同一社区内不同方向的绕行倍数相差 3.7 倍，直线距离在该地块无法作为可达性指标。

**二是评估成本高、难以定位盲区。** 人工普查无法规模化；静态统计只能给出总量，无法回答"哪一片区域既没有菜市场也没有药店"。

### 3.2 等时圈的计算方式

百度地图开放平台不暴露底层路网图，无法直接运行最短路算法。一个自然的想法是：从中心点向四周发射线，找到每条射线上 15 分钟的边界点，依次连接成多边形。

该做法存在系统性偏差。我们在合成场景（2.4 km 见方，含一条不可穿越的河道与唯一桥梁，以 8 连通栅格 Dijkstra 结果为真值）上做了对照实验：

| 采样配置 | 采样点数 | 极坐标连点 IoU | IDW + 等值线 IoU |
| --- | ---: | ---: | ---: |
| R=36, Δr=150 m | 396 | 0.785 | **0.941** |
| R=36, Δr=200 m + 阈值加密 | 396 | 0.785 | **0.932** |
| R=36, Δr=100 m | 576 | 0.785 | **0.958** |

极坐标连点得到的是内接星形多边形，会把所有凹角切除，而凹角对应河湾、封闭小区等最需要识别的区域，因此面积被系统性低估。其误差由模型偏差主导而非采样密度决定：射线数从 12 增加到 144，IoU 仅从 0.90 升到 0.94。

本项目的做法是将射线采样仅用于取数，多边形从耗时场中提取：

```
射线采样（R=36 × Δr=200 m + 阈值附近局部加密 ≈ 396 点）
→ PAVA 保序回归单调化（消除路网吸附造成的抖动）
→ 逐射线求根，定位 5/10/15 分钟穿越区间
→ IDW(k=8, p=2) 重建 25 m 规则栅格耗时场（含屏障遮蔽）
→ contourpy marching squares 提取等值线
→ shapely 修复拓扑（处理 contourpy 的重复点问题）
```

在同等采样量（396 点）下，IoU 由 0.785 提升至 0.941。

### 3.3 配额约束下的工程设计

个人开发者配额是硬约束，其中地点检索为 100 次/日。围绕该约束做了三项设计：

| 手段 | 效果 | 依据 |
| --- | --- | --- |
| 多关键字并集检索 | 8 类民生设施从 8~24 次请求压缩到 **2 次** | 实测确认配额**按请求计费**（2 次请求 = 配额 2%） |
| 多档位共享采样 | 5/10/15 三档从 924 条路线降到 **396 条** | 单元测试对比 |
| 快照 + 离线回放 | 评审方可**零配额**跑通全流程 | 采集后 replay 复跑结果一致 |

容错与降级机制包括：按服务分桶的令牌桶（2.5 QPS）、SQLite 配额账本（80% 黄色 / 95% 红色告警）、参数哈希缓存（命中不计配额）、按服务分别处理的错误分类（百度各 API 的错误码语义不一致），以及命中不可用端点时自动熔断并切换备用路线接口。

所有降级都会写入报告的 `meta.degrade_reasons` 并在界面上显示，不会静默返回不完整数据。

### 3.4 AI 层的职责划分

本项目属于开源 AI 工具赛道，但主体是确定性地理计算。AI 层的作用是将计算结果转换为可读的报告文本，不参与数值计算。

约束为：所有数值由确定性引擎产出，大模型只负责解释、归因与表达。

- **规范条文检索**：知识库收录《城市居住区规划设计标准》GB 50180-2018、《完整居住社区建设标准（试行）》、《上海市 15 分钟社区生活圈规划导则》、商务部《城市一刻钟便民生活圈建设指南》共 4 份规范 32 条条文。模型输出强制遵循 JSON Schema，每条结论需引用规范出处。
- **数值一致性校验**：提示词要求仅可引用给定指标，缺失时须写明数据不足；输出后再用正则抽出全部数字，与报告数值集合比对，不一致则带反馈重新生成，仍失败则降级为规则模板。
- **对抗测试**：构造"要求模型编造 25 处菜市场、30 所小学、95.0 分"的注入用例。模型拒绝了注入；强制喂入编造 JSON 时，校验环节也能拦截并降级，规则模板自身同样通过数值自检。
- **无 Key 可用**：未配置大模型密钥时走规则模板，Schema 与字段完全一致。

## 四、开发过程中定位的两个平台问题

**问题一：JSAPI 4.0 已移除 `BMapGL.AreaMask`。** 官方文档页面仍在介绍 GL 时代的用法，但 4.0 中 `typeof BMapGL.AreaMask === 'undefined'`。4.0 的对应能力是 `new BMapGL.MapMask(ring, opts)` 配合 `map.addFocusMask()`。压暗效果经像素级验证：同一截图内圈内平均亮度 169.8，圈外 92.5。

**问题二：官方入口脚本只能用同步 `<script>` 标签加载。** `https://api.map.baidu.com/api?type=webgl&v=4.0&ak=…` 返回的是引导脚本，它通过 `document.write` 注入真正的 1.1 MB 地图库，而 `document.write` 仅在文档解析期有效。改用 `createElement('script')` 异步注入会被浏览器忽略：不报错、控制台无输出、网络面板无请求，但 `window.BMapGL` 始终为 undefined。解决方案是直接加载真实库地址 `/getscript?v=4.0&ak=…`，并保留劫持 `document.write` 作为回退。

这两个问题的共同点是均不产生报错，但功能完全失效，排查成本较高。

## 五、测试与实测数据

### 5.1 现场实测（广州软件学院）

> 中心点：广州软件学院（BD09 `23.458320, 113.502141`）
> 方式：高驰运动手表连续轨迹记录，共 2417 个轨迹点，含时间戳

| 指标 | 实测值 |
| --- | --- |
| 总历时 | 47.4 分钟 |
| 总里程 | 3.36 km |
| 平均步速 | 1.18 m/s |
| 距中心最远 | 345 m |

**验证方法。** 若某点在录制开始后第 T 秒被实际走到，则该点从中心步行可达的时间不超过 T 秒（实际路线含绕行与折返，只会更久），因此它必须落在系统的 T 分钟等时圈内。反之则说明系统高估了可达范围。

| 项 | 结果 |
| --- | --- |
| 参与检验的轨迹点 | 2417 |
| 越界点数 | **0** |
| 越界率 | **0.00 %** |

手表输出 WGS-84 坐标，系统等时圈为 BD-09，两者在本地区相差约 500 m，所有空间判定均先做坐标系转换。

**适用范围。** 本次为单侧检验。实测最远到达 345 m，未触及 15 分钟圈（边界半径 177~825 m），因此该结果可证明等时圈没有画小，不能证明没有画大。详见 [真实对比测试报告](真实对比测试报告.md)。

## 六、复现方式

```bash
# 方式一：离线模式（零 API 配额）
cp .env.example .env          # 无需填入任何密钥
./scripts/run.sh --offline    # 或 ./scripts/run.ps1 -Offline
# 浏览器打开 http://127.0.0.1:8000

# 方式二：Docker
docker compose up
```

离线模式不需要任何密钥，也不需要联网调用百度接口。等时圈与 POI 数据来自仓库内 `data/seed/` 快照，可完整复现体检报告全流程。
