## 1. 设计原则：先把源头收紧，再做下游清洗

多数队伍的做法是「先召回一堆脏数据，再想办法洗」。本方案反过来：

> **第 0 级（L0）源头收敛是整条流水线里收益最大的一级。**

具体做法是**用官方 POI 分类名当检索词**，而不是口语词：

| 民生设施 | ❌ 口语词 | ✅ 官方二级分类名（本项目 `query`） | 效果 |
| --- | --- | --- | --- |
| 菜市场 | 「菜市场」 | `农贸市场$菜市场$生鲜市场` | 官方分类表里**没有「菜市场」这个字面词条**，但有「菜店 / 农贸市场 / 水产海鲜市场」 |
| 药店 | 「药房」 | `药店$药房` | 精确命中 |
| 小学 | 「小学」 | `小学` | 精确命中，可避开「培训机构」 |
| 社区医疗 | 「社区医院」 | `社区卫生服务中心$诊所$综合医院` | 官方分类为「医疗 > 综合医院 / 诊所」 |
| 超市便利店 | 「超市」 | `超市$便利店` | 精确命中 |
| 养老设施 | 「养老院」 | `养老院$敬老院$日间照料中心` | 官方五级表里**无「养老院」字面**，但有「养老服务」「疗养院」 |
| 公交站 | 「公交站」 | `公交车站` | 精确命中 |
| 公园绿地 | 「绿地」 | `公园$广场` | 精确命中 |

配套参数：`scope=1`（只要 name / location / uid / tag，省带宽）、`page_size=20`、`is_light_version=true`、
圆形检索时 `radius_limit=true`；v3 的 `type` 参数用作**二次筛选**（注意：v2 的 `tag` 只是「分类偏好」不是过滤器）。

**权威字典**：官方《POI 展示分类表》（五级、**1,486 条**，官方 CDN 直链可下载）作为下游归类字典（L5）。
实测存在的关键条目：**菜店 ✅ / 农贸市场 ✅ / 水产海鲜市场 ✅**（无「菜市场」）、**药店 / 中药店 / 西药店 ✅**、
**小学 / 幼儿园 / 托儿所 ✅**、**社区卫生服务中心 ✅ / 卫生院 ✅ / 诊所 ✅ / 综合医院 ✅**、
**养老服务 ✅ / 疗养院 ✅**（无「养老院」）、**公交站 ✅ / 地铁站 ✅**、
**公园 / 城市公园 / 国家湿地公园 / 绿地 / 绿地公园 ✅**、**超市 / 大型超市 / 果蔬超市 / 生鲜超市 ✅**。

## 2. 7 级流水线

方法论参照 **POI conflation 系统综述（arXiv:2310.15320）** 与 **IJGI 10(11):779** 的
「坐标统一 → 标准化 → 空间分块 → 候选对生成 → 多属性打分 → 判定 → 合并溯源」七步框架。

每一级都输出 `(kept, dropped, reasons[])`，全流程留下**可展示的清洗日志**（前端画「清洗漏斗图」）。

| 级 | 名称 | 规则 | 输出 |
| --- | --- | --- | --- |
| **L0** | **源头收敛** | 官方二级分类名做 `query`；v3 `type` 二次筛选 | 精度前置（不计入漏斗分母，因为它发生在请求参数里） |
| **L1** | **归一化** | 全角→半角；去首尾空白与不可见字符；统一中英文括号；名称内空白折叠；**去通用后缀**（店 / 分店 / 有限公司 / （xx路店））；**去括号内容**；繁简统一；数字统一（１号→1号）；拼音首字母编码处理同音异写 | 归一化名 `norm_name` |
| **L2** | **精确去重** | ① 同 `uid` → 保留信息最全的一条；② `(norm_name, geohash7)` 相同 → 合并 | 去重计数 |
| **L3** | **聚类合并**（多属性相似度打分） | `DBSCAN(eps=50 m, minPts=2)` 空间分块 → 块内加权相似度打分（见 §3） | 设施数 + 复核队列 |
| **L4** | **坐标漂移校正** | 系统性偏移用坐标转换服务消除；局部随机漂移用高置信控制点拟合局部多项式/分块仿射；与「同名簇中心」偏移 > 150 m 且无详情页 → 判漂移 | 漂移点 + 控制点 RMSE |
| **L5** | **类型纠正** | 名称关键词 + 官方分类 tag **双证据**规则表（见 §4）；归类字典用官方五级表 | 纠正日志 + 低置信队列 |
| **L6** | **可达性分层** | 圈内 / 临界（< 500 m）/ 圈外（本地 point-in-polygon，**0 配额**） | 覆盖统计输入 |

### 2.1 L2 的两条精确去重规则为什么有效

- **同 `uid`**：百度自己给同一实体在不同检索词下可能返回不同 `uid`，但同一个 `uid` 一定是同一实体 → 保留字段最全的一条；
- **`(norm_name, geohash7)`**：geohash7 ≈ **153 m × 153 m** 的格子，把「名字一样 + 位置在同一个格子」判为重复，
  能抓住「同名连锁店」在**同一位置**被多次召回的情况，又不会误杀真正分布在多处的同名连锁（不同格子 → 保留）。

> ⚠️ **注意 `uid` 一定存在，但可能重复的实体没有相同 `uid`**——百度在多关键字并集检索下，
> 同一实体可能以不同 `uid` 出现在两个关键字的结果里。因此 L2 必须**两条规则并用**。

## 3. L3 聚类合并：加权相似度打分

**空间分块**：`DBSCAN(eps = 50 m, minPts = 2)`。
依据（经综述转述）：分块距离应按类型区分（餐厅 50~100 m、公园 500~1000 m），分块最小 25 m、密度高处递归细分。

**块内相似度函数**：

```text
score = 0.45 × JW(name)                  # Jaro-Winkler：对短字符串与共同前缀敏感，适合 POI 名称
      + 0.20 × token_set(addr)         # 长地址改用 token-set，避免 JW 对长串失真
      + 0.15 × (type 一致 ? 1 : 0)
      + 0.20 × (1 − d / 150 m)         # 空间接近度，150 m 归一化
```

**判定规则（双阈值）**：

| 条件 | 动作 |
| --- | --- |
| `JW ≥ 0.85` 且 `d ≤ 50 m` | **自动合并** |
| `0.70 ≤ JW < 0.85` 且 `d ≤ 30 m` | **合并并标记待复核**（进入人工/规则复核队列） |
| 其余 | 保留为独立设施 |

**合并后的主记录选取**：
① 坐标取**加权中位数**（抗离群，比均值更稳）；
② 主记录按「来源权威度 → 字段完整度 → 时效」排序选取；
③ **保留合并溯源**（`merged_from: [uid, ...]`），便于评审质疑时逐条回查。

**权重的依据**：综述中多篇采用「名称 / 地址 / 类型 / 距离」四要素方案；
Jaro-Winkler 对短字符串与共同前缀敏感，适合 POI 名称；长地址改用 token-set。

## 4. L5 类型纠正规则表（可配置化）

采用**名称关键词 + 官方分类 tag 双证据**，避免单证据误判。
规则表放在配置文件（`config/facility_rules.yaml`）而不是硬编码，便于逐条单测。

| 规则 | 条件 | 动作 |
| --- | --- | --- |
| 菜市场**升格** | 名称含「菜市 / 农贸 / 菜场 / 生鲜」且 tag ∈ {市场, 商铺} | 归入 **菜市场** |
| 菜市场**降格** | tag = 购物 > 市场 且名称含「建材 / 家具 / 花鸟 / 五金 / 汽配」 | **剔除** |
| 小学**排除** | tag ∈ {培训机构, 成人教育, 亲子教育} 且名称不含「小学」 | **剔除**（避免把补习班当小学） |
| 社区医院**识别** | tag ∈ {综合医院, 诊所} 且名称含「社区卫生服务 / 社区医院 / 卫生服务站 / 地段医院」 | 归入 **社区医院** |
| 养老**识别** | 名称含「养老 / 敬老 / 日间照料 / 颐养 / 托老 / 长者照护」 | 归入 **养老设施** |
| 便利店**归并** | tag = 购物 > 便利店 或名称含「便利店 / 便利蜂 / 全家 / 罗森 / 7-11」 | 归入 **超市便利店** |

**置信度与降级**：

- 类目映射**置信度 < 0.95** 的映射对进人工审核（依据 IJGI 10(11):779 的做法）；
- 低置信结果标 `type_uncertain`，**不参与盲区强断言**——它可以出现在覆盖统计里，但不能成为「此处无药店」的判决依据。

## 5. L4 坐标漂移校正

| 子步骤 | 做法 |
| --- | --- |
| ① 系统性偏移 | 用坐标转换服务消除（WGS84 ↔ GCJ02 ↔ BD09 的整段偏移是确定性的） |
| ② 局部随机漂移 | 以**高置信匹配对**（`JW ≥ 0.95` 且 `d ≤ 20 m`）为控制点，拟合局部多项式 / 分块仿射；**报告控制点 RMSE** |
| ③ 离群判定 | 与「同名簇中心」偏移 > **150 m** 且**无详情页** → 判定为漂移，剔除或降权 |
| ④ 验证手段 | POI 与道路中心线 / 建筑轮廓叠加，统计「**落在建筑外的比例**」与**平均偏移向量场** |

> ⚠️ **诚实声明**：本项目**没有**道路中心线 / 建筑轮廓底图，
> 因此 ④ 的验证指标（落建筑外比例、偏移向量场）属于**设计预留**，
> 当前实现只能给出 ② 的控制点 RMSE 与 ③ 的离群计数。**该指标标注为待验证。**

## 6. 清洗漏斗（CONTRACT.md §4 冻结字段）

```jsonc
"cleaning_funnel": { "raw": 320, "deduped": 268, "corrected": 254, "inside": 186 }
```

| 字段 | 口径定义 | 对应流水线 |
| --- | --- | --- |
| `raw` | **本地裁剪前**的原始召回条数（所有关键字组、所有切片求和，含重复） | L0 之后 |
| `deduped` | 经 **L1 + L2** 去重后的条数 | L1–L2 |
| `corrected` | 经 **L3 合并 + L4 漂移剔除 + L5 类型纠正**后的**有效设施数**（剔除了降格项、合并了重复项） | L3–L5 |
| `inside` | 经 **L6** 裁剪后**落在 15 分钟等时圈内**的设施数 | L6 |

> 上表的 `320 / 268 / 254 / 186` 是 **CONTRACT.md 中的示例值**，
> 用于前后端联调时对齐字段语义，**不是某个真实社区的实测结果**。
> 真实社区的漏斗数字由 S1 在采集 seed 快照时产出，填入
> [docs/report/真实对比测试报告模板.md](../report/真实对比测试报告模板.md)。

**为什么漏斗本身是交付物的一部分**：评分表把「必须做多源 POI 数据清洗」写进 FR-3，
漏斗图能让评审**一眼看到每一级到底丢了多少、为什么丢**——这比一句「我们做了清洗」有力得多。

## 7. 每类设施的统计口径（FR-3 要求四项输出）

| 输出字段（CONTRACT.md §4） | 定义 |
| --- | --- |
| `count` | 圈内设施数量（`inside` 按类别拆分） |
| `density_per_km2` | `count / 等时圈面积(km²)`（面积取 `isochrones["15"].area_m2`） |
| `nearest_walk_seconds` | **最近一处的真实步行耗时**（来自批量算路，**不是直线距离**） |
| `coverage_score` | 0~1 覆盖率评分（评分模型见 SOLUTION §4.5） |

> `nearest_walk_seconds` **必须是真实路网耗时**。若该类别在圈内没有设施，
> 则取**临界设施**（圈外 < 500 m）的真实耗时并标注，而不是回落到直线距离估算——
> 否则「最近一处步行耗时」这个字段就失去了它相对于直线距离的意义。
