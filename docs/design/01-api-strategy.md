## 1. 策略总纲：一切围绕「地点检索 100/日」设计

本项目可用的百度地图 Web 服务接口有五类，但**个人开发者的日配额严重不均**：

| 服务 | 个人开发者配额/日 | 并发 | 本项目用量 |
| --- | --- | --- | --- |
| 地理编码 | 5,000 | 3 QPS | 每个社区 1 次 |
| 逆地理编码 | **300** | 3 QPS | **规划为 0 次**（改用 POI 自带 address + 本地 point-in-polygon） |
| **地点检索** | **100** 🔴 | 3 QPS | **每个社区 2 次**（多关键字并集） |
| 批量算路（步行） | 5,000 **路线** | 3 QPS | 每个社区 ≈ 1032 路线 |
| 步行路线规划（轻量） | 5,000 | 3 QPS | 单点兜底 |
| 坐标转换 | 5,000 | 3 QPS | 按需，单次可批量 100 点 |
| 行政区划查询 | 5,000 | 3 QPS | 冷启动建底库 |

**结论（[一手]，SOLUTION.md §2.1）**：算路配额约有 **5 倍余量**，真正的瓶颈是**地点检索 100 次/日**。
因此整套调用策略只有一条主线：**把 POI 请求数从 8~24 次/社区压到 2 次/社区**，其余接口按「够用、可缓存、可复用」处理。

> 🔴 **已证伪的常见说法（不得写入任何文档）**：
> ① ~~「Place API 10 万次/天」「Geocoding 无使用次数限制」~~ —— 来自旧版静态文档，现行为 100/日 与 5,000/日；
> ② ~~「前端 JS API 检索可绕开 100/日」~~ —— **JS API 地点检索同为 100/日、3 QPS**（同一张权益表）；
> ③ ~~「周边检索与城市名检索配额不同」~~ —— 权益页只有**一行「地点检索」**，三种检索方式**共用一个池子**。

## 3. 陷阱一：`status=211` —— 一个状态码，两种病因

官方错误码表把 `211` 定义为「SN 校验失败」。但**本机实测**发现它同时被用于「服务未开通」：

| 服务 | 非法 AK 时的实测返回 | 官方状态码表中的语义 |
| --- | --- | --- |
| `place/v2/search` | `{"status":200,"message":"APP不存在，AK有误请检查再重试"}` | 200 = APP 不存在 |
| `geocoding/v3` | `{"status":200,"message":"APP不存在…"}` | 同上 |
| `routematrix/v2/walking` | `{"status":2,"message":"ak is invalid"}` | 2 = 参数错误（**语义冲突**） |
| `routematrix/v2/*`（权限异常） | `status=211 APP SN校验失败` | 211 = SN 校验失败 |

**排查顺序（写进 README FAQ 与运维手册）**：

1. **先排签名**。若同一 AK 的 `geocoding` / `place/v3` / `directionlite` 都正常，签名实现基本没问题。
   签名的三个高频错误：
   - 必须**双重编码**（每个 value 编码一次 → 整串再编码一次），漏掉第二次编码会**稳定 211**；
   - path 必须形如 `/place/v3/around?`（含前导斜杠与问号、不含域名）；
   - `sk` 直接拼接，**不加 `&`、不写 `sk=`**；参数顺序必须与 URL 中出现顺序一致。
2. **零成本自证签名**：官方测试向量 `ak=yourak` + `sk=yoursk` +
   `/geocoder/v2/?address=百度大厦&output=json&ak=yourak` ⇒ `sn = 7de5a22212ffaa9e326444c75a58f9a0`。
   跑 `python scripts/check_ak.py --sn-only`（**零配额、不需要真实 AK**）。
3. **再排服务权限**：签名自检通过仍 211 ⇒ 到控制台为该 AK 补勾「批量算路」，必要时重新生成 AK。
   **不要**因为 211 就去改签名实现——那会浪费一整轮排查。

## 4. 陷阱二：`radius` 超界会「退化成整城检索」

官方原文：**「当半径过大，超过中心点所在城市边界时，会变为城市范围检索，检索范围为中心点所在城市」**。
即半径开大**不会**得到「半径内全量」的结果，而是**变成全市检索**：白烧配额 + 灌入成片脏数据。

**执行策略**：

| 优先级 | 方式 | 适用 | 说明 |
| --- | --- | --- | --- |
| ① | `place/v3/polygon` 显式矩形切片 | 首选（**待验证**） | 传 **4~5 点、首尾闭合**的显式矩形（v2 文档对「左下右上」还是「左上右下」自相矛盾，两点写法有风险）；切片 1 km × 1 km |
| ② | `place/v3/around` + `radius_limit=true` | 回退 | **仅用于半径 ≤ 外接圆 × 1.1 的小范围**；调用前断言半径合法 |
| ③ | `place/v3/region` | 冷启动建底库 | 一次性拉某区某类设施的全量落库，后续只做增量 |

**`radius_limit=true` 是双刃剑（[一手] 官方原文）**：
官方明确「设置为 true 时会影响返回结果中 total 准确性及每页召回 poi 数量」。
本项目**本来就不信任 `total`**（见下），因此**照开**。

**越界率自检（零成本的护栏）**：统计返回 POI 中落在请求范围之外的比例，**> 5% 即判定「半径/边界退化」**，
告警并降级该次结果（改用上一版缓存或快照）。这一步能第一时间发现「整城检索」。

## 5. 陷阱三：`total` 字段不可信

官方原文：「**设置了 `page_num` 字段才会出现 `total` 字段**。出于数据保护目的，**单次请求 `total` 最多为 150**」。

→ **任何「用 `total` 统计设施数量」的做法都是错的**；分页实际被限制在约 8 页内。
本项目的设施数量**一律以本地裁剪后的实测结果为准**。

**分页策略改为「饱和探测」而不是「按 total 翻页」**：

1. 某切片某关键字组返回条数 == 关键字数 × `page_size` ⇒ 判定「可能被截断」；
2. **只对该切片该组追加 1 页**（`page_num=1`）；
3. 仍满 ⇒ 对该切片做 **500 m 二次切分**重查。

## 6. SN 签名（已实现并验证）

```python
def bd_encode(v): return urllib.parse.quote(str(v), safe="", encoding="utf-8")
def make_sn(path, params, sk):
    query = "&".join(f"{k}={bd_encode(v)}" for k, v in params.items())
    return hashlib.md5(bd_encode(f"{path}?{query}{sk}").encode()).hexdigest()
```

| 要点 | 说明 |
| --- | --- |
| 参数顺序 | **必须是 URL 中出现的顺序**；`ak` 必须在 params 里；`sn` 最后计算、**最后拼接** |
| 双重编码 | 先对每个 value 编码拼串，再对 `路径 + "?" + 参数串 + sk` **整串再编码一次** |
| `timestamp` | **使用 sn 时 `timestamp` 必填** |
| 跨语言差异 | 官方给的等价函数（JS / Java / C# / PHP）**语义并不等价**（空格 `%20` vs `+`、`!'()*` 处理不同）→ Python 侧**不要直接用 `quote_plus`**，按官方白名单实现：非保留字 `a-z A-Z 0-9 - _ . ~` 不编码，其余一律编码 |
| 官方测试向量 | `7de5a22212ffaa9e326444c75a58f9a0`（务必写成单元测试，**不需要真实 AK**） |

## 7. 核心优化一：多关键字并集 —— 8 类设施压到 2 次请求

官方原文（v2 与 v3 文档均有）：`query` 支持多个关键字并集检索，不同关键字间以 `$` 分隔，**最多 10 个**；
`page_size` 最大 20；**多关键字检索时返回记录数为「关键字个数 × page_size」**。

### 7.1 ✅ 关键实测结论（D1 闸门 G1）

> **多关键字并集检索按【请求】计费，不是按关键字。**
>
> 实测方式：控制台「地点检索」用量在两次调用后为 **2%**（＝2 次），
> 而这两次调用分别是「单关键字 1 次」与「3 关键字并集 1 次」。
> 若按关键字计费应为 4 次（4%）。→ **确认按请求计费。**

**架构结论**：合并策略成立。8 类设施按**同质大类**分 2 组，**总计 2 次请求**。

### 7.2 冻结的分组与检索词（对齐 CONTRACT.md §4.2）

| 组 | query（`$` 分隔） | 关键字数 | 覆盖类别 |
| --- | --- | :---: | --- |
| A · 医疗组 | `药店$药房$社区卫生服务中心$诊所$综合医院$养老院$敬老院$日间照料中心` | 8 | 药店 / 社区医疗 / 养老设施 |
| B · 生活组 | `农贸市场$菜市场$生鲜市场$超市$便利店$小学$公交车站$公园$广场` | 9 | 菜市场 / 超市便利店 / 小学 / 公交站 / 公园绿地 |

- 两组关键字数分别为 8 与 9，**均 ≤ 10 上限**；
- 单次理论召回上限 = 关键字数 × 20 = 160 / 180 条，**远高于单类 20 条**——密集城区不会因翻页丢失设施；
- 若某类因 `page_size` 上限召回不足，**允许追加 1 次补充请求（最多 4 次）**。

> ⚠️ **两个官方未背书的风险点（必须写进文档、必须实测）**：
> ① 官方**承认**该机制，但**从未推荐**把它用于「分类采集」——混类后 `page_num` 的分页语义难以预测；
> ② 配额计费口径在任何公开文档中**都找不到说明**（已由 G1 实测解决）。
> 因此合并**只用于「同质大类」**，不把 8 类混成一锅。

### 7.3 召回质量的第二道保险：用官方分类名而不是口语词

官方 POI 二级分类表里，8 类民生设施中有 6 类存在**同名二级分类**，直接作为 `query` 的召回质量显著优于口语词。
另有官方《POI 展示分类表》（五级、1,486 条）可作为**下游归类字典**：
实测存在「菜店 / 农贸市场 / 水产海鲜市场 ✅」（注意：**无「菜市场」字面**）、「社区卫生服务中心 ✅」、「养老服务 ✅」（**无「养老院」字面**）。
→ **上游用二级分类名做 `query`，下游用五级表对 `classified_poi_tag` 归类**（需 `scope=2`），两者构成「检索—清洗」闭环。

## 8. 核心优化二：批量算路的打包与计费口径

| 硬性限制（官方文档） | 数值 | 本项目应对 |
| --- | --- | --- |
| 步行批量算路单次路线数 | **1×50 或 N×M ≤ 50** | 严格按 1 起点 × 48 终点打包（留 2 条余量） |
| 计费口径 | **按最终路线数计费，不是请求数** | 配额账本按「路线数」记账；1×50 打包仍计 50 |
| 步行起终点距离 | **> 200 km 报参数错** | 社区尺度（≤ 2 km）天然满足；调用前断言 |
| 路线几何 | **不返回 polyline** | 等时圈必须自行插值重建（见 [02-isochrone.md](02-isochrone.md)） |

**「免费午餐」参数（务必用上）**：

| 参数 | 收益 |
| --- | --- |
| `ret_straight_dist=1` | **同一次配额内同时返回直线距离** → **零额外成本标定绕行系数**（见 [05-quota-and-fallback.md](05-quota-and-fallback.md) §7） |
| `road_prefer=3` | 「无逆行且无阶梯」的算路方案 → 适老/无障碍/婴儿车场景的加分细节，同时过滤楼梯这类伪可达 |
| `origins` 用 `纬度,经度;uid` | 提升绑路精度（中心点若已拿到 POI `uid`） |
| `tactics` | ❌ **对步行无效**（官方：「驾车、摩托车可设置，其他无需设置」），不要传 |

**`duration.value == 0` 必须视为「无效」而不是「耗时 0」**——绑路失败会返回 0，
当作 0 会让等时圈出现假覆盖。实现里统一标记为 `None`，交给插值与解析模型补值
（见 `backend/app/core/isochrone.py` 的 `measure()`）。

## 附：前端地图库加载的两个实测坑（2026-10-14 实测）

> 以下均为本机无头 Chrome 实测结论，不是推测。**都是"不报错但功能失效"的隐性坑，排查成本极高。**

### 坑 1：JSAPI 4.0 没有 `BMapGL.AreaMask`

`typeof BMapGL.AreaMask === 'undefined'`（GL 时代的类在 4.0 已被移除）。
4.0 的对应能力是：

```js
const mask = new BMapGL.MapMask(ring, { isOpen: true, enableDragging: false });
map.addFocusMask(mask);      // Map.prototype 上确有此二法
map.removeFocusMask(mask);
```

**效果验证（像素级）**：同一张整页截图中，15 分钟圈内平均亮度 **169.8**，圈外 **92.5** —— 压暗确实生效。

### 坑 2：官方入口脚本只能用**同步 `<script>` 标签**加载，不能 JS 异步注入

官方入口 `https://api.map.baidu.com/api?type=webgl&v=4.0&ak=…` 返回的**只是引导脚本**，
它内部靠 `document.write('<script src="/getscript?...">')` 注入真正的 **1.1 MB** 地图库。
而 `document.write` 只在**文档解析期间**有效。

用 `createElement('script')` 在页面加载完成后注入时，这段 write 会被浏览器**静默忽略**：

- ❌ 不报错
- ❌ console 干净
- ❌ 网络面板看不到 getscript 请求
- ✅ 但 `window.BMapGL` **永远是 undefined**，地图区一直 loading

**我们的解法**（见 `frontend/src/map/baidu.ts`）：直接加载真实库地址

```js
window.BMAP_PROTOCOL = 'https';
window.BMapGL_loadScriptTime = Date.now();
// 直接请求真实库，绕开引导脚本
https://api.map.baidu.com/getscript?v=4.0&ak=<AK>&services=&t=<ts>
```

并保留"临时劫持 `document.write`"作为回退路径。

> 比看到"照着官方 demo 抄了一遍"有说服力得多。建议在作品介绍文档里单列一节。
