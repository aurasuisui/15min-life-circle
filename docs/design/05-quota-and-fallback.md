# 05 · 配额治理与容错降级

> 交付物对应：任务书 NFR-1「API 配额与限流」、NFR-2「容错与降级机制」——
> 后者是评分表里**权重第二高（30%）且明确点名的考点**。
> 事实来源：[docs/SOLUTION.md](../SOLUTION.md) §5、§2.1、§2.6、[docs/CONTRACT.md](../CONTRACT.md) §3.3

---

## 1. 一句话结论

> **配额治理的目标不是「多调用几次」，而是「一次都不浪费」；
> 容错的目标不是「永远不失败」，而是「失败时用户知道，且结果仍然可用」。**

两条铁律：

1. **配额耗尽的请求绝不重试**（重试只会白烧配额，还拖慢降级）；
2. **任何降级都必须让用户看得见**（NFR-2 明文：「不得静默返回错误结果」）。

## 2. 四道防线（按收益排序）

```text
                          ┌─────────────── 真实 API 调用 ───────────────┐
请求 → ①缓存 → ②Single-Flight → ③令牌桶(2.5 QPS) → ④配额账本(80/95/100%) → 百度地图
         │            │                  │                    │
         └──命中即返回 └──合并并发         └──排队而非拒绝       └──熔断即降级
```

| # | 防线 | 作用 | 关键参数 |
| --- | --- | --- | --- |
| **①** | **缓存 CacheStore**（收益最大） | 同参数重复分析**命中不计配额** | 键 = `sha256(service ‖ 归一化参数 ‖ 数据版本)`；坐标量化到 **5 位小数（≈1 m）**；TTL：地理编码 **90 天** / POI **7 天** / 算路 **30 天** / 行政区划 **30 天** |
| **②** | **Single-Flight 合并** | 同一 `(center, params)` 的并发请求合并为**一次**真实调用，其余 await 同一 Future | `asyncio.Lock` + Future 共享；防前端连点 / 多标签页 / 演示时误触 |
| **③** | **令牌桶 TokenBucket** | 不越 3 QPS 的官方上限 | `rate = 2.5, burst = 3`（**留 17% 余量**），**按服务分桶**；**排队而非拒绝** |
| **④** | **每日配额账本 QuotaLedger** | 进程重启不丢账；提前熔断 | SQLite 持久化；`reserve(n)` → 调用 → `commit(n)` / 失败 `release(n)`；**80% 黄灯提示 / 95% 自动切 seed 红灯 / 100% 抛 `QuotaExhausted`** |

### 2.1 配额账本的数据结构

```sql
CREATE TABLE quota_usage (
  day TEXT, service TEXT, used INTEGER, "limit" INTEGER,
  reserved INTEGER, updated_at TEXT,
  PRIMARY KEY (day, service)
);
```

- 调用前 `reserve(n)`（`used + reserved + n ≤ limit` 才放行）——**预留机制**让并发请求不会集体冲过上限；
- 调用后 `commit(n)`；失败则 `release(n)`（**失败不扣配额**，与百度的实际计费口径保持一致）；
- 与百度控制台实际用量做**日终对账**（`scripts/quota_reconcile.py`），修正漂移。

### 2.2 计费单位的坑（必须按服务区分）

| 服务 | 计费单位 | 后果 |
| --- | --- | --- |
| 地点检索 | **按请求**（已实测：多关键字并集仍计 1 次） | 合并关键字 = 直接省配额 |
| 批量算路 | **按最终路线数**，不是请求数 | 1 起点 × 50 终点打包**仍计 50**；`N×M ≤ 50` 是硬上限 |
| 地理编码 / 坐标转换 | 按请求（坐标转换单次可批 100 点） | 批量转换是免费的效率 |

> 如果账本按「请求数」记账，批量算路会**严重低估**消耗（以为 9 次、实际 432 路线）。
> 这是最容易写错、后果最严重的一处——账本必须按**路线数**记账。

## 3. 错误分级处置表

**前提（本机实测，SOLUTION §2.6）**：百度**不同服务对同一状态码的语义并不一致**——
非法 AK 时 `place/v2/search` 返回 `status=200`，而 `routematrix/v2/walking` 返回 `status=2`。
因此分类器必须是 `(service, status, message)` **三元组**，而不是全局状态码字典。

### 3.1 通用分级处置

| 情形 | 识别 | 处置 | 重试 |
| --- | --- | --- | --- |
| **天配额耗尽** | `status=4` / `302`，message 含 `Quota Failure` | **快速失败**，账本置满，立即切 seed / 解析模型，前端显式提示 | ❌ **绝不重试** |
| 并发超限 | `status=401` | 令牌桶降速 + 抖动退避 | ✅ 指数退避 ×3 |
| 瞬时故障 | HTTP 5xx / 超时 / 连接重置 | 指数退避 + **全抖动**，上限 3 次 | ✅ |
| 参数错误 | place `status=2` / `4`，route `status=2` | 记录并**跳过该点**（单点失败不拖垮整批），纳入 `degradations[]` | ❌ |
| **SN / AK 失败** | `status=211` / `200` / `5` | **立即熔断 + 告警**，绝不重试 | ❌ |
| 服务被禁用 | `status=240` / `261` | 熔断该服务，走降级链 | ❌ |
| IP 白名单失败 | `status=210` | 报错终止（提示改用 SN 签名） | ❌ |
| 单点算路无解 | `duration.value == 0` | 标记 `None`，走插值 / 解析模型补值 | ❌ |

### 3.2 按服务细化（**必须区分**）

| 服务 | 状态码 | 含义 | 处置 |
| --- | --- | --- | --- |
| `place/*` | 200 | APP 不存在 / AK 有误（**不是成功！**） | 报错终止 |
| `place/*` | 2 | 参数错误 | 跳过该点 |
| `routematrix/*` | 2 | **ak is invalid**（语义与 place 冲突） | 报错终止 |
| `routematrix/*` | **211** | SN 校验失败**或服务未开通** | **先查签名、再查权限**（见 [01-api-strategy.md](01-api-strategy.md) §3） |
| 任意服务 | 0 | 成功 | — |
| 任意服务 | 101 / 200 / 210 / 240 | AK 非法 / IP 白名单 / 服务禁用 | 报错终止 |

> ⚠️ **关键实现约束**：分类器必须拿到 `service` 上下文，且要**同时匹配 message 文本**
> （`ak is invalid` vs `参数错误`）才能可靠区分。只按数字码分类一定会误判。

## 4. 降级链与「绝不静默」

```text
live API ──(失败/配额)──▶ 本地缓存 ──(未命中)──▶ seed 快照 ──(无)──▶ 解析模型
   │                                                                        │
   └────────────── 每一步都写入 meta.degraded / degrade_reasons[] ◀──────────┘
```

### 4.1 对外契约（CONTRACT.md §4 冻结字段）

```jsonc
"meta": {
  "data_mode": "live",              // live | replay | mock
  "degraded": false,                // 任一环节降级则为 true
  "degrade_reasons": [],            // ["POI 配额不足，使用快照", ...]
  "quota": { "routes_used": 432, "routes_limit": 5000,
             "poi_used": 3, "poi_limit": 100 }
}
```

**`degraded` 与 `degrade_reasons[]` 不是日志，是 API 契约的一部分**——
前端必须据此在结果卡片顶部显示提示，例如：

> ⚠️ 本次结果数据完整度 78%：3 类设施来自离线快照（采集于 2026-10-10），等时圈由解析模型估算。

### 4.2 解析降级模型（最后一道）

`t(x) ≈ (dist_straight(x) × u + crossing_penalty) / v_walk`

| 参数 | 取值 | 依据 |
| --- | --- | --- |
| `u` 绕行系数 | 1.25（老城密网）/ **1.35（一般城区，默认）** / 1.5（郊区、封闭小区、河网） | Marti & Weidmann 2016（步行 1.2–1.5，瑞士实测 1.24–1.39）；Boscoe 2012（驾车 1.417，r²=0.94） |
| `τ_cross` 过街惩罚 | 15–40 s（长周期主干道 40–60 s） | HCM `d_p = 0.5·C·(1 − g/C)²`；ATRF 2025 实测 +2.5%~12.2% |
| `v_walk` | 1.25 m/s（适老 / 儿童 1.0–1.1 m/s） | 与等时圈采样同一常数 |

**零成本标定（必须做）**：批量算路的 `ret_straight_dist=1` 在**同一次配额内同时返回直线距离**，
于是可以抽 300~500 个 O-D 对（按 200/400/800/1200/1600 m 分层各 60~100 对）做 Huber 稳健回归，
按距离分箱估 `u(d)`，再按方位角与是否跨河/跨铁路分组估屏障项，输出 `u` 的 95% CI 与残差 MAPE。
**残差 MAPE ≤ 10% 即足以支撑盲区预筛。** 当前状态：**待验证**（依赖批量算路可用）。

### 4.3 数据完整度怎么算（前端提示里那个 78%）

**当前为设计约定（待实现核验）**：

> 数据完整度 = 各类设施中**来自 live / 本地缓存**的类别数占 8 类的比例 × 0.6
> 　　　　　 + 等时圈是否由**真实算路**产出（是 1、否 0）× 0.4

即：**等时圈是否降级是权重最大的一项**——因为它是整个体检的地基。
该公式写在文档里是为了让「完整度」这个词**可核算、可复现**，而不是一个拍脑袋的百分比。

## 6. 配额不足时的回退方案（§5.4 备案）

**触发条件**：若将来发现多关键字合并被改为**按关键字计费**，或批量算路配额被下调。

| 措施 | 效果 |
| --- | --- |
| **每日 N 社区硬上限** + 社区白名单预采集 | 把 100 配额花在演示用的 2~3 个社区上 |
| **seed 数据集 + replay 默认开启** | 评审方零配额跑通（本就必需，不是回退项） |
| **POI 快照跨日复用**（TTL 7 天） | 同一社区 7 天内只消耗 1 次 |
| **降采样**：只对 15 min 圈内的核心区做全类别，边缘区只做关键 3 类 | 请求数减半 |
| **`is_light_version=true`** | 提升平响，为翻页争取时间预算 |
| **降低等时圈采样密度**（Δr 200 m → 300 m） | 路线数线性下降，代价是 IoU 下降（见 [02-isochrone.md](02-isochrone.md) §3.1） |

## 7. 三条「有测试证明」的容错要求（评分表原文）

任务书要求「POI 缺失 / API 异常 / QPS 限流均有兜底，且**有测试证明**」。对应测试清单：

| # | 注入的故障 | 期望行为 | 断言 |
| --- | --- | --- | --- |
| 1 | `place` 返回 `status=4`（配额耗尽） | 快速失败 → 切 seed → `degraded=true` | **调用次数 == 1（不重试）**；`degrade_reasons` 含配额原因 |
| 2 | `routematrix` 返回 `status=401`（QPS 超限） | 指数退避重试 | 重试次数 ≤ 3；最终成功或降级 |
| 3 | HTTP 500 / 连接超时 | 指数退避 + 全抖动 | 退避间隔递增且有抖动 |
| 4 | `status=211` | **立即熔断，不重试** | 调用次数 == 1；返回 AK/权限类错误提示 |
| 5 | `duration.value == 0` | 标记 `None`，不当作「耗时 0」 | 该点不产生 `t=0` 的假覆盖 |
| 6 | 同一 `(center, params)` 并发 10 次 | Single-Flight 合并 | **真实调用次数 == 1** |
| 7 | 重复分析同一社区 | 命中缓存 | **第二次配额消耗 == 0** |
| 8 | LLM 超时 / 无 Key | 模板化降级 | `ai_report.degraded == true`，API **不返回 5xx** |
| 9 | `app.ai` 模块不存在或抛异常 | S1 自产最简模板 | API **不返回 5xx**（CONTRACT.md §6.2 硬性要求） |

> 单测用 `respx` 打桩（已装），**全程零网络**；再加 `MockProvider` 保证算法层也不需要网络。

## 8. 已知局限（诚实声明）

| # | 局限 | 说明 |
| --- | --- | --- |
| 1 | **SQLite 账本是单机账本** | 多实例部署会各记一份账，需要换成 Redis 或中心化存储。当前部署形态为单容器，**不构成问题**，但要在架构文档里写明 |
| 2 | **百度控制台用量与本地账本可能存在漂移** | 靠 `scripts/quota_reconcile.py` 日终对账修正；**对账脚本尚未实现**（待验证） |
| 3 | 日容量从「50 社区/日」修正为「≈4.8 社区/日」 | 这是 G1 实测带来的**结论反转**，必须以实测为准 |
| 4 | 解析模型的标定未完成 | §4.2 的标定流程已设计，但依赖批量算路可用（当前 211） |
| 5 | 数据完整度公式为设计约定 | 已在 §4.3 写明算式，**实现与核验待补** |
| 6 | 配额数字的最终确认 | 官方文档页不列数字，配额只在控制台展示；上线前需二次确认 |
